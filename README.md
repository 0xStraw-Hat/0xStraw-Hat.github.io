## 1. Start the local preview

Open PowerShell and run:

```powershell
Set-Location 'E:\strawhat-blog-anime-v1'
hugo server --bind 127.0.0.1 --port 1318 --baseURL http://localhost:1318/ --buildDrafts --disableFastRender
```

Open **http://localhost:1318/**. Leave PowerShell running. Save your Markdown or data file and Hugo refreshes the preview. **Ctrl+C** stops the server.

`--buildDrafts` shows unfinished posts locally, including the preserved old `Test` draft. Without that flag, drafts are hidden. If another server already uses 1318, use the existing one or stop it before starting another. The comparison design is archived and its old preview on port **1317** is stopped.

Hugo Extended **0.154.5** is installed on this computer. Check with `hugo version`. You only need Hugo to run this site; Node and Python are optional development checks, not requirements for writing posts.

## 2. Create a post

From the project folder:

```powershell
hugo new content --kind post post/my-first-writeup
```

Replace `my-first-writeup` with your actual lowercase slug, using hyphens between words. This creates:

```text
content/
  post/
    my-first-writeup/
      index.md
```

Open `content/post/my-first-writeup/index.md` in your editor. Keep the filename **index.md**, not `_index.md`. The URL will be `/post/my-first-writeup/`. Avoid changing the folder name after publication, because that changes the URL.

The settings between the `+++` lines are TOML front matter:

```toml
+++
title = 'Finding a parser bug with fuzzing'
date = '2026-09-11T18:00:00+03:00'
draft = true
description = 'How I found, minimized, and understood a parser crash.'
categories = ['Notes']
tags = ['Fuzzing', 'C']
# Uncomment after placing cover.jpg beside index.md:
# cover = 'cover.jpg'
+++
```

Keep the date generated by Hugo, or set your real publication date and timezone. The date above is only an example.

| Setting | What it does |
|---|---|
| `title` | Article heading and title in the logbook |
| `date` | Publication date and article order |
| `draft = true` | Hides the post from normal builds |
| `description` | Short summary on listings and in metadata |
| `categories = ['Notes']` | Places it under the Notes filter |
| `categories = ['CVE']` | Places it under the Research filter |
| `tags` | Topics available in the Logbook topic filter |
| `cover` | The image used on the card, article banner, and adjacent-post navigation |

Use the category spelling **CVE** for Research: that is the current theme's filter value. This category does **not** claim a CVE as your discovery or add it to the CVEs page; discoveries are managed separately in `data/cves.toml`.

Tags such as `C++`, `Format String`, and `Fuzzing` are supported. Keep capitalization consistent to avoid duplicate-looking topics. New posts appear automatically in the homepage, logbook, archives, search, RSS, and previous/next navigation when included in the build.

For titles containing apostrophes, use double quotes, for example `title = "A parser's assumptions"`. Write the article below the closing `+++`.

## 3. Add pictures and a cover

For a new post, keep its images beside its Markdown:

```text
content/post/my-first-writeup/
  index.md
  cover.jpg
  crash.png
  minimized-input.png
```

In the article body:

```markdown
![Debugger showing the invalid memory access](crash.png)

![The minimized input that triggers the bug](minimized-input.png)
```

For the cover, add this inside the front matter:

```toml
cover = 'cover.jpg'
```

The cover is separate from body images. Add a Markdown image line if you also want that picture inside the article. If `cover` is omitted, the theme uses the anime city artwork.

A subfolder works too:

```text
content/post/my-first-writeup/images/crash.png
```

```markdown
![The crash in the debugger](images/crash.png)
```

Use short lowercase filenames with hyphens and match capitalization exactly. Prefer PNG for debugger screenshots and JPEG/WebP for large scenery. Keep screenshots legible and avoid uploading enormous source images unnecessarily. Put explanatory text in the `[...]` so the picture has a meaningful description.

### Shared images and older posts

An image at `static/images/shared-example.png` is referenced as:

```markdown
![An example shared between posts](/images/shared-example.png)
```

The browser URL never includes `static/`. Never use a Windows path such as `E:\pictures\crash.png` in Markdown: copy the file into the project first.

Existing posts use `static/posts-imgs/` and `static/posts-cover/`. Those continue to work; you do not need to reorganize published posts. Never put source images in `public/`, because Hugo regenerates that directory.

The recommended new-post layout follows Hugo's [page bundle model](https://gohugo.io/content-management/page-bundles/).

## 4. Write Markdown and code

Copy the structure you need:

````markdown
A short introduction: what you investigated and why.

## Setup

Explain the environment and prerequisites.

### Build the target

```bash
cc -g -fsanitize=address target.c -o target
```

## Analysis

Use **bold** for emphasis, *italics* for an aside, and `inline_code`
for a function, command, filename, or variable.

- First observation
- Second observation

![The relevant debugger output](crash.png)

> **Note:** A useful detail for the reader.

[Project source](https://github.com/torvalds/linux)

## Takeaways

Explain the root cause and what you learned.
````

Use `##` for main sections and `###` for subsections. The theme generates the table of contents from those headings; the page title already supplies the top-level heading.

Specify the language after the opening code fence: `c`, `cpp`, `python`, `bash`, `go`, or `text`, for example. Code blocks **longer than 15 lines automatically collapse to a 15-line preview** with Expand/Collapse controls. You do not need special Markdown. Copy code copies the full block, and printing includes the full code.

Write ordinary Markdown rather than raw HTML; raw HTML rendering is disabled in this project.

## 5. Add a CVE or GitHub advisory

The same records feed **the homepage sidebar, CVEs page, About page, and record counter**. Edit the data once; do not manually edit those pages.

### Add a CVE

Open `data/cves.toml` and add a new `[[entries]]` block. This is a template: replace the placeholder ID, project, date, summary, and URL before making it public.

```toml
[[entries]]
id = 'CVE-YYYY-NNNNN'
target = 'Project name'
summary = 'One short sentence explaining the vulnerability.'
kind = 'Discovery'
date = '2026-09-11'
severity = 'Moderate'
advisory = 'https://project.example/security/the-advisory'
draft = true
# Optional, when your local write-up is published:
# article = '/post/my-first-writeup/'
# Optional, ONLY if the advisory publishes a numeric score:
# score = 5.3
# cvss_version = '3.1'
```

- Replace the example severity with the published severity: `Critical`, `High`, `Moderate`, `Low`, or `None`.
- When there is a published numeric score, add both `score` and `cvss_version`. Supported versions are `3.0`, `3.1`, and `4.0`. Do not infer a number from a severity label.
- If there is no published numeric score, leave those two fields out. The page displays the severity and explains that no numeric score is published.
- `advisory` links to the project's original advisory. If omitted, CVE records fall back to cve.org.
- `article` is optional. Add it only when the referenced local write-up is available in the normal build.
- Keep `kind = 'Discovery'`. Reproduction exercises belong in articles, not your discovery list. The Xpdf exercise remains an article only.
- Change `draft = false` when the record is public and ready to display. Each ID should appear once in its data file.

**Data drafts differ from post drafts:** `draft = true` in these TOML files always hides the record, even when the preview uses `--buildDrafts`. Set it to false to preview its published presentation. Data dates are display metadata; they do not schedule publication. Use the draft field to control visibility.

### Add a GitHub Security Advisory

Open `data/advisories.toml` and append:

```toml
[[entries]]
id = 'GHSA-xxxx-yyyy-zzzz'
target = 'Project name'
summary = 'One short sentence explaining the vulnerability.'
severity = 'Moderate'
date = '2026-09-11'
url = 'https://github.com/OWNER/REPO/security/advisories/GHSA-xxxx-yyyy-zzzz'
draft = true
# Add only if published:
# score = 5.3
# cvss_version = '3.1'
# article = '/post/my-first-writeup/'
```

Use **`url` for GHSA entries** and **`advisory` for CVE entries**. Fill in the real information, then set `draft = false`.

GHSAs appear first in their file order; CVEs follow in descending score order. The counter counts public records, not necessarily unique vulnerabilities when a GHSA and CVE describe the same issue. Its project count is based on distinct `target` values, so use consistent project names.

`draft` controls website visibility, not access to your repository. Anything committed to a public GitHub repository, including draft text, is public source.

## 6. Change friends and buttons

Edit `data/friends.toml`. There are two groups, in this order:

1. **Friends:** Cubeyond, followed by your blog.
2. **Random stuff:** your GitHub, Linux source, Neovim, Python, IDA, Hugo, and RSS.

Other people’s buttons use their original hosted image URLs. Add this inside the Friends group, **before the next `[[groups]]` header**:

```toml
[[groups.buttons]]
name = 'Friend name'
image = 'https://their-website.example/button.png'
url = 'https://their-website.example/'
# Optional provenance, not the clickable destination:
source = 'https://where-the-button-came-from.example/'
```

Reorder blocks to reorder the buttons. Optional `alt` supplies a longer image description. For remote animated artwork, set `animated = true`; reduced-motion visitors get a text link instead. Only your own button is stored locally, with a still frame for reduced-motion preferences and printing. There is no visible pause control.

Use `url = '/'` for this blog and `url = '/index.xml'` for this blog's RSS. The GitHub entry uses `site_param = 'github'`, so it follows the GitHub URL in `hugo.toml`. Use either `url` or `site_param` on an entry.

The shelf stays on the homepage. `data/blogroll.toml` is the old inspiration list and no longer drives it. More detail: [FRIENDS-BUTTONS.md](docs/FRIENDS-BUTTONS.md).

## 8. Publish a new post

Run these commands in the source project, never inside `public/` or the old generated website checkout.

1. Write and preview with `draft = true`.
2. Add the post's images and cover.
3. Set `draft = false` and choose a publication date that is not in the future.
4. Stop the local server with Ctrl+C, then build and commit:

```powershell
Set-Location 'E:\strawhat-blog-anime-v1'
hugo --minify --destination .checks/site
# Continue only if Hugo finishes successfully.
git status
git add content/post/my-first-writeup
git diff --cached --stat
git diff --cached
git commit -m "Publish parser fuzzing write-up"
git push
```

Replace the folder and commit message with yours. Keeping images beside `index.md` means `git add content/post/my-first-writeup` stages both text and images.

If you used shared images, stage their actual paths too:

```powershell
git add static/images/my-shared-image.png
```

For a CVE, advisory, or friends-only update, stage the changed data and any added assets instead:

```powershell
git add data/cves.toml
# If you changed these too, include them:
# git add data/advisories.toml
# git add data/friends.toml static/images/buttons
# git add content/about.md data/about.toml
git diff --cached
git commit -m "Add a public vulnerability disclosure"
git push
```

On GitHub, open the source repository's **Actions** tab. Wait for both the build and deployment to finish successfully, then visit the live page. A successful push alone does not mean the deployment succeeded.

`hugo` builds files locally. `git commit` records changes locally. `git push` uploads those commits. An activated GitHub Actions workflow is what builds and publishes the website.

Do not commit `public/`, `.checks/`, `build-check/`, or `.hugo_build.lock`; the included `.gitignore` excludes them. Do not use the original blog's `deploy.sh` for this source workflow.

## 10. Troubleshooting

| Problem | What to check |
|---|---|
| Post is missing locally | Use `--buildDrafts`, check its date, and confirm it is in `content/post/` |
| Post is missing after publication | Set `draft = false`, use a non-future date, push the commit, and check Actions |
| CVE/GHSA is missing | Check its data-file `draft`; post preview flags do not override it |
| New topic is missing | Add it to `tags`, save, and make sure the post is included in the build |
| Image works locally but not on GitHub | Match filename case, commit the image, and use bundle or `/images/...` paths |
| Image is stretched or unreadable | Use the original image proportions and a legible screenshot; covers are cropped by the design |
| Hugo reports a TOML error | Check quotes, commas, bracket pairs, and repeated section headers; the error names the file |
| CVE build validation fails | Use a real CVE ID, `kind = 'Discovery'`, a supported severity/version, and a score between 0 and 10 if supplied |
| Port 1318 is in use | Reuse the running preview or stop it with Ctrl+C; do not start a second server on the same port |
| `git` says this is not a repository | Complete the one-time setup, or switch to the actual source repository |
| Push succeeds but the site stays old | Read the latest Actions run and verify the custom domain points to the repository you deployed |
| Push is rejected because the remote changed | Fetch and review those commits before merging/rebasing; do not solve it with a blind force-push |

### Before publishing a change
